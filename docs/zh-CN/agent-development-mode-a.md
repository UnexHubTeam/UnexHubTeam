面向 Agent 开发者 · 模式 A / 平台托管独立节点 · 技术预览

文档版本：0.1 预览　更新日期：2026-09-29

> **重要：** 模式 A 已有部署配置、镜像校验、调度和计费组件，但三种应用拓扑均未完成生产验证。`single` 与 `split` 当前提供没有平台逐请求鉴权的直接 HTTP 入口，只能使用模拟数据和受信任测试用户。`frontend-package` 的 ZIP 控件当前被模式授权阻止，无法完成模式 A 上传；客户端鉴权、查询参数和刷新恢复也仍有限制。模式 B 的 Cloudflare 容器流程同样存在凭据安全限制，不能视为适用于所有场景的生产安全保证。

模式 A 将 Agent 安排到由平台登记、管理和调度的独立节点。开发者准备镜像或前端包、填写运行配置并完成开发者自测；平台负责从可用节点中分配整机。它**不表示**平台会为开发者自动购买云服务器，也不表示应用运行在 Kubernetes 中。平台还必须独立交付并验证真实节点上的运行时；页面或 API 存在不表示节点运行时自动可用。节点准备和运维由平台侧完成，不属于本指南的开发者操作。

请在平台界面选择“模式 A”，不要从旧示例复制部署值，也不要通过 API 提交未公开说明的值。需要 Cloudflare 容器流程时，请改用[模式 B 开发与上传指南](agent-development-upload.md)。

<a id="section-1"></a>
## 1. 技术预览范围

模式 A 的开发者流程是：

1. 选择适合应用的拓扑；当前镜像流程使用 `single` 或 `split`，`frontend-package` 的完整上传流程仍被阻止。
2. 按当前上传和校验流程要求构建 `linux/amd64` OCI 镜像，并向平台确认节点兼容性与所需硬件。可提前在本地准备和测试静态前端 ZIP。
3. 将镜像推送到 Registry，在部署配置中校验 digest、扫描结果和所需的平台副本。
4. 保存端口、健康检查、启动方式、节点规格下限和空闲时间等配置。
5. 待平台确认真实节点运行时可用于测试后，核对镜像拉取、入口、模型调用、停止行为和实际运行 digest。
6. 提交上架审核，审核通过并得到平台针对目标用户场景的发布确认后，用户才可选整机规格与时长并启动。

### 当前能力边界

| 能力 | 技术预览状态 | 开发者应如何处理 |
| --- | --- | --- |
| 独立节点调度 | 平台从已管理的节点库存中分配整机；节点运行时需独立交付并验证 | 不编写自动购机或 Kubernetes 配置；无可用节点时联系平台方 |
| 系统与架构 | 当前镜像上传和校验流程要求 `linux/amd64` | 向平台确认所选节点兼容这一镜像目标，并满足应用的硬件要求 |
| `single` | 配置入口已存在；直接 HTTP 访问 | 仅在受信任测试环境验证，不能假设具有用户鉴权或 HTTPS |
| `split` | 配置入口已存在；前端作为直接 HTTP 入口 | 同样仅用于受信任测试；后端路由需确认，前端镜像回填与独立私有仓库凭据选择尚不完整 |
| `frontend-package` | 表单有 ZIP 控件，但当前模式授权阻止模式 A 完成上传 | 完整流程尚不可用；客户端鉴权、查询参数和刷新恢复也有限制 |
| 持久化 | 未提供模式 A 服务端持久化保证 | 将节点文件系统视为临时数据；需要长期数据时使用经平台确认的外部服务 |
| 外部 Registry | 已有镜像引用入口；支持公开镜像和平台加密保存的私有仓库只读凭据 | 平台校验成功不代表节点能拉取；节点的只读拉取能力需单独验证 |
| 平台镜像仓库 | 平台配置 TCR 后才显示 Docker Push 入口，当前只应用于受信任测试 | 更广泛使用需具备按 Agent 限定权限的写凭据；不要把仓库凭据写入应用 |
| 浏览器镜像上传 | OCI 或 `docker save` TAR 上传尚未提供 | 源码 ZIP 或 `docker export` 文件系统 TAR 不能替代可运行的 OCI 镜像 |

“独立节点”描述的是平台的整机调度单位，不自动等同于永久磁盘、专用公网入口、端到端网络隔离或生产安全认证。应用上线前仍需对所选拓扑单独完成安全与可用性验收。

本指南中的行为都属于需在每次发布前重新核对的预览契约。若平台当前界面或运营说明提出更严格要求，应以更严格的现行要求为准。

模式 A 的用户在启动前，从满足 Agent 最低要求且有库存的整机 SKU 中选择规格和最长时长；模式 B 的运行规格由已发布 Agent 版本固定。应根据应用需求和平台确认的发布条件选择流程，不能仅凭部署表单可见或上传完成就认定可以生产运行。

<a id="section-2"></a>
## 2. 选择应用拓扑

### 三种拓扑对比

| 拓扑 | 需要交付 | 用户入口 | 适合验证的场景 | 当前限制 |
| --- | --- | --- | --- | --- |
| `single` | 一个包含页面与 API 的 OCI 镜像 | 镜像公开的直接 HTTP 端口 | 单体 Web 应用、最短集成路径 | 入口无平台逐请求鉴权；只限受信任测试 |
| `split` | 前端 OCI 镜像 + 后端 OCI 镜像 | 前端镜像的直接 HTTP 端口 | 前后端已拆分、且平台已确认后端运行时路由的项目 | 入口无平台逐请求鉴权；服务发现、前端镜像回填和独立私有仓库凭据仍有限制 |
| `frontend-package` | 静态前端 ZIP + 后端 OCI 镜像 | 设计上由平台托管前端，并通过相对 `api/...` 代理到后端 | 先在本地准备和验证静态制品 | 当前模式授权阻止 ZIP 上传，完整流程不可用；鉴权、查询参数与刷新也有限制 |

没有一种拓扑可以仅凭“平台表单中可选择”就认定为生产验证通过。开发者需要以当前制品、当前 digest 和平台当前环境重新测试。

### 如何选择

- 应用已是一个同时提供网页和 API 的镜像：优先用 `single` 做功能验证。
- 项目必须分别构建前端和后端镜像：只有平台已确认当前环境的后端运行时路由时才试用 `split`；让每个镜像保留自己的默认启动命令，并逐一测试。
- 前端能够构建为纯静态文件：可在本地准备 `frontend-package` 制品，等待平台启用并验证模式 A ZIP 上传后再测试完整流程；业务 API 还需完整的打开与客户端鉴权流程通过验证。
- 需要公开互联网访问、强用户鉴权、可靠刷新恢复或服务端持久化：当前模式 A 技术预览不能单独满足这些要求；发布前应等待平台确认方案。

不要为了绕过入口限制，把模型 Key、启动令牌或会话标识写入前端包、URL、浏览器存储或镜像。

<a id="section-3"></a>
## 3. 准备应用与运行制品

### 后端和容器要求

| 项目 | 要求与建议 |
| --- | --- |
| 系统与架构 | 所有运行镜像必须为 `linux/amd64`，当前上传和校验流程不支持其他架构；向平台确认所选节点兼容这一目标并满足应用的硬件要求 |
| 监听地址 | 监听 `0.0.0.0`，前端和后端容器端口均须在 `1024–65535` 范围内，并与平台表单完全一致；本文示例使用 `8080` |
| 健康检查 | 提供快速返回 HTTP 200 的路径，例如 `GET /health`；不调用模型或外部慢服务 |
| 主进程 | 保持前台运行，正确处理 SIGTERM，并在有限时间内取消请求和退出 |
| 权限 | 使用非 root 用户；不依赖特权容器、宿主网络、Docker Socket 或任意宿主目录 |
| 日志 | 记录请求编号、阶段、耗时和状态；不记录 Key、Authorization、令牌或完整敏感输入 |
| 文件系统 | 按临时数据处理；启动时应能从干净文件系统恢复工作 |
| 网络调用 | 设置连接和响应超时；前端取消或断开后终止不再需要的上游请求 |

`EXPOSE 8080` 只声明端口，不能代替应用实际监听。平台表单中的端口、镜像监听端口和健康检查端口必须一致。

各拓扑还需满足：

- `single` 的镜像端口、应用监听、健康检查和平台端口必须指向同一个服务；当前还需填写已经在本地验证过的启动命令。
- `split` 分别配置前端与后端镜像和端口。除非同一条命令确实适用于两个镜像，否则不要填写共享覆盖命令。
- `frontend-package` 先准备后端镜像、端口、健康检查和已验证的启动命令，供上传能力启用后测试；前端包只包含静态资源，不包含运行时秘密。

### 各拓扑的制品

建议使用不会覆盖的唯一版本标签，并记录对应的 Registry digest。除非仓库强制标签不可变，否则标签仍可能被移动；只有 digest 才是制品的不可变身份。示例名称如下：

```text
single:
  registry.example/team/my-agent:0.1.0-preview.1

split:
  registry.example/team/my-agent-frontend:0.1.0-preview.1
  registry.example/team/my-agent-backend:0.1.0-preview.1

frontend-package:
  dist/frontend-0.1.0-preview.1.zip
  registry.example/team/my-agent-backend:0.1.0-preview.1
```

镜像引用只是示例，请替换为真实 Registry。现有外部 Registry 入口支持公开镜像，也支持选择由平台加密保存的私有仓库只读凭据。平台完成镜像校验与目标节点能够只读拉取是两项独立检查；私有镜像还需确认平台副本和节点读取能力。不要把 Registry 凭据写入应用、镜像层或前端。

前端 ZIP 应满足：

- `index.html` 位于解压后的包根目录。
- JS、CSS、字体和图片使用相对路径，能在非根路径下加载。
- 不包含 `.env`、源码映射中的秘密、Registry 凭据或平台运行时凭据。
- 不把固定域名、用户 ID、Agent ID、会话标识或启动令牌编译进包内。

`split` 中的两个镜像应各自带有可工作的默认命令。只有平台已经为当前环境确认独立命令配置时，才覆盖镜像默认命令；不能假设同一条自定义命令同时适合前端和后端。

<a id="section-4"></a>
## 4. 接入运行时凭据与配置

平台在后端运行环境注入以下变量：

| 变量 | 含义 | 使用规则 |
| --- | --- | --- |
| `UNEX_API_KEY` | 当前用户与 Agent 配对的托管模型 Key | 只在后端内存中读取，作为 Bearer 凭据使用 |
| `UNEX_API_BASE_URL` | 与该 Key 配套、已包含 `/v1` 的版本化模型 API Base URL | 与 Key 成对使用，只追加 `/chat/completions` 等具体端点，不替换为硬编码域名 |
| `UNEX_AGENT_ID` | 当前 Agent 标识 | 与平台注入的 `UNEX_USER_ID` 组合用于逻辑分区与诊断，不要求用户填写 |
| `UNEX_USER_ID` | 当前用户标识 | 与平台注入的 `UNEX_AGENT_ID` 组合使用，不信任前端自行提交的替代值 |

`UNEX_API_KEY` 和 `UNEX_API_BASE_URL` 必须来自同一次平台注入并成对使用。不要把其中任何一个写进前端响应、静态包、镜像层、错误正文、分析工具或浏览器存储。`UNEX_AGENT_ID` 与 `UNEX_USER_ID` 也应由后端读取，不能当作浏览器可以任意声明的授权凭据。

将注入的 Key 视为长期、高价值的托管凭据，不要假设停止或重新启动某个会话就会使它失效。若怀疑发生泄露，应立即停止测试、通知平台方，并按平台的凭据处置与轮换流程处理。

仅在后端保存不代表 Key 已与开发者控制的镜像、依赖或有运行时访问权限的运维人员隔离。当前注入方式不能作为不受信任第三方代码的安全凭据边界，也不构成生产环境的凭据隔离承诺。此兼容流程只应用于受信任的预览代码和测试用户；生产使用需要平台确认合适的凭据或模型调用边界。

不要要求普通用户填写托管 Key，也不要接受浏览器提交的 Base URL 后再把托管 Key 转发过去。两个注入 ID 仅用于可信后端上下文中的逻辑分区与诊断，不能替代业务授权检查。

下面的 Python 片段仅演示配置读取：

```python
import os

def model_request_config():
    api_key = os.environ.get("UNEX_API_KEY", "").strip()
    base_url = os.environ.get("UNEX_API_BASE_URL", "").rstrip("/")
    agent_id = os.environ.get("UNEX_AGENT_ID", "")
    user_id = os.environ.get("UNEX_USER_ID", "")
    if not api_key or not base_url:
        raise RuntimeError("Managed model credentials are unavailable")
    endpoint = f"{base_url}/chat/completions"
    headers = {"Authorization": f"Bearer {api_key}"}
    return endpoint, headers, agent_id, user_id
```

平台注入的 Base URL 已包含 `/v1`，只追加具体端点，禁止重复拼接版本路径。只在业务请求边界检查模型凭据，让 `/health` 在凭据缺失时仍可正常返回运行状态；业务接口应返回清晰的配置错误，而不是泄露环境变量。

自定义变量使用应用自己的前缀，例如 `APP_MODEL`、`APP_LOG_LEVEL`。不要在自定义变量区域覆盖 `UNEX_*`，也不要把 Registry 密码或个人模型 Key 作为“临时变量”提交给应用。

<a id="section-5"></a>
## 5. 适配拓扑与用户入口

### `single`：单镜像入口

同一个进程或镜像同时提供页面和业务 API。优先使用同源相对路径，例如 `/api/chat`，并验证根页面、静态资源、健康检查与 API 都通过平台给出的实际入口工作。

当前直接入口是未经平台逐请求鉴权的 HTTP 地址。知道或发现地址的人可能绕过平台页面访问应用，因此只能在隔离、受信任的测试环境中使用。不要放入真实用户数据，不要将“在平台点击打开”误解为后续每个 HTTP 请求都已鉴权。

### `split`：前后端镜像

前端是用户入口，后端只负责 API。开发者需要验证：

1. 两个镜像都为 `linux/amd64`，并可各自启动；平台已确认节点兼容性与所需硬件。
2. 前端只使用平台为当前环境明确提供并验证的后端路由，不硬编码开发机、节点或旧实例地址。
3. 后端监听配置端口，健康检查不依赖前端。
4. 浏览器请求满足当前入口的同源与 CORS 规则。
5. 停止实例后，前后端都能退出且不继续处理请求。

当前没有开发者可以普遍假定的后端服务发现地址；若平台没有为当前环境提供并验证明确路由，应停止接入而不是自行设计地址。`split` 的公开入口与 `single` 具有同样的直接、无平台逐请求鉴权 HTTP 限制，也只能用于受信任测试。

重新打开部署表单时，前端镜像字段目前不能可靠地从已保存记录恢复。请记录两个镜像引用和 digest，每次保存或再次提交前重新核对。当前也尚未完整支持前后端位于不同私有 Registry 时分别选择凭据；使用这种组合前，应与平台确认受支持的只读拉取方案。

### `frontend-package`：托管静态前端与 API 代理

表单虽然显示前端 ZIP 上传控件，但当前后端模式授权不允许模式 A 完成该上传。因此 ZIP 上传、发布与启动的端到端流程目前不可用；不要通过提交其他部署模式来绕过限制。

前端包应使用相对资源。设计中的后端入口是相对 `api/...` 路径，但当前打开流程不能可靠地向客户端提供 API 代理所需的鉴权上下文。因此，在平台提供并验证正式客户端流程前，不得宣称业务 API 可用，也不要通过读取、保存或自行转发启动令牌来绕过限制。

当前技术预览需要特别注意：

- 完整鉴权流程可用后仍需重新测试 API 代理；当前代理可能无法完整保留查询参数。不要依赖 `?user=...`、`?cursor=...` 或查询参数中的路由状态完成关键流程。
- 非敏感业务输入可放在路径段或请求正文中，但身份与权限仍必须由可信后端上下文确定。
- 刷新页面可能丢失当前启动上下文或临时界面状态。提供“返回平台重新打开”的提示，不把刷新恢复作为已保证能力。
- 不要用 `localStorage` 保存启动令牌、会话参数或其他秘密来绕过刷新限制。

应先解除并验证 ZIP 上传授权，再验证完整客户端流程；这些限制尚未完成生产验收，`frontend-package` 不能作为可用的生产交付路径。

<a id="section-6"></a>
## 6. 数据保存与生命周期

模式 A 当前没有向 Agent 开发者提供已保证的服务端持久化。容器内文件、内存、临时目录和节点本地目录都可能在停止、重建、故障恢复或重新调度时丢失。

平台表单中的 `storage_gb` 是运行配置字段，**不表示**已经创建持久卷，也不构成容量、备份、恢复、迁移或跨会话保留承诺。不要根据填写的数值向用户宣传“云盘”或“数据永久保存”。

普通用户通过 Agent 上传的业务文件，未明确接入经批准的外部存储时，都应按会话临时数据处理。应提示用户停止会话后文件可能丢失，并在会话中提供导出。前端 ZIP、计划中的镜像归档等发布制品暂存不属于普通用户的持久工作区；发布流程使用 R2 也不意味着用户数据已经持久化。

| 数据类型 | 当前建议 |
| --- | --- |
| 缓存、临时导出、可重新生成文件 | 可暂存在容器内，但必须允许随时丢失 |
| 页面主题、非敏感筛选项、可丢弃草稿 | 可少量暂存在浏览器 `localStorage`，并提供清除与降级行为 |
| API Key、Authorization、启动令牌、会话参数 | 禁止写入 `localStorage`、`sessionStorage`、IndexedDB 或前端包 |
| 敏感对话、用户文件、付费结果、必须恢复的记录 | 不能依赖节点磁盘或浏览器存储；使用经平台批准并明确配置的外部持久化服务 |

浏览器 `localStorage` 只是一种当前浏览器与来源域下的便捷缓存，不属于平台持久化。它可能被用户或浏览器清除，不能可靠跨设备、跨浏览器或跨用户同步。尤其在 `frontend-package` 技术预览中，刷新后可能无法恢复原启动上下文，因此即使缓存仍存在，也不能把它当作可继续原会话的依据。

若应用必须保存数据，应在发布前与平台确认外部数据服务、身份隔离、加密、备份、删除、费用和合规要求。未完成这些确认时，应把 Agent 设计为无状态或仅处理可丢弃数据。

## 7. 构建并在本机验证

### 构建当前要求的 `linux/amd64` 镜像

当前上传和校验流程要求所有运行镜像为 `linux/amd64`，不支持其他镜像架构；还需向平台确认所选节点兼容这一目标并满足应用的硬件要求。在 Apple Silicon 或其他架构的开发机上，也应明确设置 `--platform linux/amd64`，不能使用本机默认值：

```bash
docker buildx build \
  --platform linux/amd64 \
  --provenance=false \
  --load \
  -t registry.example/team/my-agent:0.1.0-preview.1 .

docker image inspect registry.example/team/my-agent:0.1.0-preview.1 \
  --format '{{.Os}}/{{.Architecture}} user={{.Config.User}}'
```

结果必须为 `linux/amd64`，并显示明确的非 root 用户。`split` 需要对前端和后端两个镜像分别构建与检查。

### 验证启动、健康检查和停止

本地验证使用模拟网关和占位凭据，不要在终端历史或脚本中粘贴生产 Key：

```bash
docker run --rm -d \
  --name mode-a-local \
  --platform linux/amd64 \
  -p 127.0.0.1:8080:8080 \
  -e UNEX_API_KEY=sk-local-placeholder \
  -e UNEX_API_BASE_URL=http://host.docker.internal:9000/v1 \
  -e UNEX_AGENT_ID=local-agent \
  -e UNEX_USER_ID=local-user \
  registry.example/team/my-agent:0.1.0-preview.1

curl --fail http://127.0.0.1:8080/health
curl --fail -o /dev/null http://127.0.0.1:8080/
docker logs --tail 80 mode-a-local
docker stop --time 15 mode-a-local
```

模拟网关应验证鉴权头存在，但不能记录完整 Key。还应验证模型流的成功、错误、取消和超时；HTTP 200 后出现流式错误时，前端必须显示失败而不是误报完成。

### 验证前端包

准备供后续平台测试的 ZIP 时，先在本地核对内容：

```bash
unzip -l dist/frontend-0.1.0-preview.1.zip
```

确认 `index.html` 位于根目录，静态资源引用为相对路径，包内搜索不到 `.env`、`UNEX_API_KEY`、Authorization 或真实服务凭据。通过本地非根路径静态服务器验证页面，不能只用 `file://` 打开。本地验证不会解除当前模式 A 的上传限制。

### 推送并记录 digest

```bash
docker push registry.example/team/my-agent:0.1.0-preview.1
docker buildx imagetools inspect registry.example/team/my-agent:0.1.0-preview.1
```

保存 Registry 返回的 `sha256:...`。标签可能被移动，digest 才能准确指向本次测试制品。不要把终端中的 Registry 登录命令、密码或完整凭据写进 README、工单或构建日志。

## 8. 配置、测试与发布

### 选择当前可用的制品入口

打开[Agent 部署配置](https://unexhub.ai/console/my_agents?tab=deploy)。下述操作说明的是现有平台页面和 API，不代表真实节点上的上传、启动和运行已经验证完成。

| 入口 | 当前状态 | 开发者操作 |
| --- | --- | --- |
| 外部镜像仓库 | 已有镜像引用入口 | 将 OCI 镜像推送到 Registry，填写完整引用；私有镜像选择平台保存的只读凭据 |
| 推送到平台镜像仓库 | 仅在平台配置 TCR 后显示，当前仅限受信任测试 | 在获准的测试环境使用页面提供的 Docker Push 命令；更广泛使用需按 Agent 授权、短期且可撤销的写凭据 |
| 浏览器 OCI / `docker save` TAR 上传 | 计划能力，当前没有开发者上传入口 | 不要把源码 ZIP、`docker export` TAR 当作镜像，也不要根据旧的“本地归档”文案推断已可上传 |
| `frontend-package` 前端 ZIP | 控件可见，但模式 A 授权阻止上传完成 | 先在本地准备并验证制品，等待上传授权及完整前端/API 流程通过验证 |

外部 Registry 的推送与 digest 检查见上一节。完整的不可变引用示例为：

```text
registry.example/team/my-agent@sha256:<published-digest>
```

私有 Registry 凭据由平台加密保存并用于只读访问，不得写入镜像层、前端代码、应用环境变量或构建日志。节点拉取能力必须单独验证：平台校验通过或 Docker Push 成功，不代表分配到的节点能读取审核镜像或它的平台副本。

### 填写平台配置

| 配置项 | 如何填写 |
| --- | --- |
| 部署模式 | 在界面选择“模式 A”；不要手工填写未公开的部署值 |
| 应用拓扑 | 当前镜像流程选择 `single` 或 `split`；`frontend-package` 需先解除 ZIP 授权阻止 |
| 镜像 | 填写完整引用，私有外部镜像选择只读凭据；分别核对平台校验、digest、扫描、副本状态和节点拉取能力 |
| 端口 | 前端和后端容器端口均须在 `1024–65535` 范围内，并与应用监听端口一致；示例为 `8080` |
| 健康检查 | 填写快速返回 200、且不调用模型的路径，例如 `/health` |
| 启动命令 | `single` 与 `frontend-package` 当前填写已验证的启动命令；`split` 优先保留两个镜像各自的默认命令，避免共享覆盖 |
| 节点规格 | 设置应用的最低要求，不自行假定云厂商机型；用户启动前从符合要求的可用整机 SKU 中选择 |
| 空闲时间 | 按应用需要填写，并在平台确认的真实节点运行时上验证停止行为 |
| `gpu_count` | 模式 A 中 `1` 表示占用一整台节点，不表示物理 GPU 数量为 1 |
| `storage_gb` | 按表单要求填写，但不能视为持久卷或数据保留保证 |
| 自定义变量 | 只填写应用配置；不要覆盖 `UNEX_*`，不要提交 Registry 或模型秘密 |

真实 GPU 数量和型号以平台展示并确认的节点规格为准。不要根据 `gpu_count=1` 修改并行度、显存预算或模型要求。

### 校验、保存、测试与提交审核

以下顺序包括开发者和平台必须核对的发布要求，不表示当前界面已经自动强制执行其中每一项。

1. 创建或选择 Agent，打开部署配置并选择“模式 A”。当前镜像流程选择 `single` 或 `split`；`frontend-package` 的完整流程仍受上述限制。
2. 选择镜像来源。`single` 填一个 `linux/amd64` 镜像引用，`split` 分别填前端和后端引用；需要时选择私有 Registry 的只读凭据，并填写 `1024–65535` 范围内的匹配容器端口和健康检查路径。重新打开 `split` 表单后要核对两个镜像，不能假设同一份凭据适用于不同私有仓库。
3. 点击“拉取并校验镜像”，核对每个组件解析得到的源 digest 和镜像扫描状态。标签不能替代审核制品的身份；生产发布还需启用并完成要求的扫描。
4. 检查平台 TCR 副本状态。模式 A 会将外部镜像排队复制到 TCR；复制失败时，在解决错误后使用复制重试操作并确认结果。私有外部镜像必须等平台副本就绪、节点只读拉取已验证后再申请发布。生产目标应要求每个组件都有可信的不可变平台副本，即使当前界面允许公开镜像提前提交审核，也不能跳过这项检查。
5. 在同页保存 `1024–65535` 范围内的前后端容器端口、健康检查、启动命令、节点规格下限和空闲时间等运行配置。`single` 当前要求填写启动命令；`split` 优先保留两个镜像各自的默认命令。`gpu_count=1` 按整机单位理解，`storage_gb` 只按配置约束处理。
6. 平台确认所选真实节点运行时已可用于测试后，再使用模拟数据运行开发者测试。核对实际 digest、镜像拉取、启动、健康检查、真实用户入口、静态资源、API、模型请求、流式响应、取消、错误、停止与重启。日志和错误不能含凭据或敏感数据；平台校验和本地容器测试不能替代这项真实节点验证。
7. 每个镜像的 digest、扫描、所需平台副本、已保存配置和适用测试均就绪后，点击“提交上架审核”。提交的 digest 必须与实际测试制品相同。审核通过，并得到平台对目标用户场景的入口和数据方案确认后，才让用户启动。

### 发布前核对 digest

每次修改镜像，即使沿用同一标签，也要视为新制品：

- **开发测试时：** 实际运行 digest 必须等于本次准备测试的候选 digest。
- **提交审核时：** 提交的 digest 必须等于已经完成上述测试的 digest。
- **面向用户发布时：** 平台显示的已批准/已发布 digest 必须等于测试通过并获批的 digest。

逐组件比较候选、实际测试、审核提交和已批准/已发布的 digest。如果不一致，停止发布，使用新版本号重新执行构建、扫描、拓扑和平台测试并提交审核。不能拿旧的已批准 digest 的测试结果证明新的当前 digest 可用，也不能只比较标签名称。保留一个已批准的可用 digest 和明确回滚步骤。

由于模式 A 仍是技术预览，完成开发者自测不等于获得生产发布资格。必须等待平台明确确认所选拓扑、入口安全和数据方案已经满足目标用户场景。

### 用户启动与计费

审核与发布获准后，用户在启动前选择满足 Agent 最低要求且有库存的整机 SKU，以及最长运行时长。这与模式 B 由已发布版本固定运行规格的流程不同。

平台在启动前从用户充值余额中预扣预估运行费用；只有实例进入 `running` 后才开始计算运行时长。上传或校验镜像不会启动最终用户的容器运行计费。模式 A 当前按整机每小时价格计费，运行时长向上取整到整小时，实结不超过预扣；启动失败或启动健康检查失败时，运行费用全额退还。模型调用与节点运行分别计费。`storage_gb` 当前不会增加持久磁盘费用，也不会提供持久磁盘。

### 计划中的上传能力

后续计划包括带进度、取消/续传和归档校验的浏览器 OCI / `docker save` TAR 上传，按 Agent 限定权限的短期 Docker Push 凭据，完整的逐组件私有 Registry 处理，以及可用的模式 A 前端 ZIP 授权和发布流程。这些是计划能力，不是当前已经开放的额外上传端点。每条路径仍需镜像 digest 校验、扫描、不可变平台副本和发布审核；制品暂存不会提供用户持久化。

<a id="section-9"></a>
## 9. 常见问题排查

| 现象 | 优先检查 | 处理方式 |
| --- | --- | --- |
| 没有可用节点或无法启动 | 所选 SKU、平台节点库存、最长运行时长 | 模式 A 不自动购机；保留错误时间和规格，联系平台方 |
| 平台校验通过但节点拉取失败 | 平台只读访问与节点拉取能力是两项独立检查 | 核对引用、digest、TCR 副本和平台确认的节点只读能力；不要把仓库凭据交给应用 |
| 平台副本等待中或复制失败 | 外部镜像尚未成功复制到 TCR | 查看复制状态，解决错误后重试，发布前核对每个组件 |
| 找不到浏览器镜像 TAR 上传 | 当前只属于计划能力 | 使用外部 Registry 入口，或在受信任测试中使用已配置的 TCR Docker Push |
| 平台镜像仓库 Push 入口不存在 | 平台尚未配置 TCR | 使用外部 Registry；若 TCR Push 入口可见，在平台确认按 Agent 限定权限的写凭据前，也只应用于受信任测试 |
| 镜像架构被拒绝，或启动出现 `exec format error` | 镜像不是 `linux/amd64`，或分配节点不兼容 | 使用 `--platform linux/amd64` 重建并检查每个镜像，同时让平台确认节点兼容性 |
| 健康检查超时 | 是否监听 `0.0.0.0`、端口和路径是否一致、检查是否调用外部服务 | 修正监听和表单；让健康检查快速、独立返回 200 |
| 模型接口返回 401 | Key 与 Base URL 是否来自同一次注入，是否被硬编码值覆盖 | 删除覆盖值；后端成对读取 `UNEX_API_KEY` 与 `UNEX_API_BASE_URL` |
| 页面能打开但入口不安全 | 是否使用 `single` 或 `split` 的直接 HTTP | 这是当前预览限制；只在受信任环境测试，不向真实用户发布 |
| `split` 前端无法访问后端 | 当前环境没有已验证的后端服务发现路由 | 不要硬编码节点地址；停止接入并向平台确认受支持的路由 |
| `split` 重开表单后前端镜像消失，或不能配置两个私有仓库 | 镜像回填与独立凭据选择尚不完整 | 再次提交前核对两个引用及 digest，并与平台确认受支持的私有拉取方案 |
| `frontend-package` ZIP 上传被拒绝 | 当前前端上传授权不允许模式 A | 等待平台修复并验证授权后再测试完整流程，不通过切换部署模式绕过 |
| `frontend-package` API 返回 401 | 当前打开流程没有向客户端提供代理所需的鉴权上下文 | 不要用暴露或持久化启动令牌的方式绕过；等待平台确认完整流程 |
| `frontend-package` API 丢失查询参数 | 请求是否依赖 `?key=value` | 避免关键流程依赖查询参数；非敏感业务输入改用路径或正文，并等待平台确认修复 |
| `frontend-package` 刷新后失去上下文 | 是否把刷新恢复当作保证 | 引导用户返回平台重新打开；不要把令牌或会话标识存入浏览器来绕过 |
| 重启后文件或记录消失 | 是否写在容器或节点本地，是否误解 `storage_gb` | 将其视为临时数据；需要长期保存时接入经批准的外部持久化服务 |
| 页面显示 GPU 数量为 1 | 是否把 `gpu_count=1` 当成物理卡数 | 它表示整机占用一台；实际硬件按平台 SKU 核对 |
| `split` 中一个容器无法启动 | 两个镜像的默认命令、端口、架构和健康检查 | 分别本地运行；不要用一条未经验证的覆盖命令套用两个镜像 |
| 更新标签后仍运行旧内容 | 当前、测试、批准和发布 digest 是否相同 | 使用不覆盖的唯一版本标签，并按 digest 重新提交、测试和审核 |

提交问题时提供：Agent ID、拓扑、应用版本、脱敏镜像引用与 digest、节点 SKU、发生时间和时区、请求编号、HTTP 状态、脱敏错误码、启动阶段和可重现步骤。不要在公开工单粘贴 API Key、Authorization、Registry 密码、启动令牌、完整入口 URL 或用户内容。

## 10. 技术预览发布检查表

发布模式 A 预览前，应核对所有适用项目。这些是发布要求，不表示每项检查当前都已自动强制执行。

### 制品与运行时

- [ ] 已选择并记录 `single`、`split` 或 `frontend-package`，没有把表单可选误写成生产验证完成。
- [ ] 所有运行镜像都为 `linux/amd64`、以非 root 运行，并能在干净环境启动；平台已确认节点兼容性与所需硬件。
- [ ] 应用监听 `0.0.0.0`，前端和后端容器端口均在 `1024–65535` 范围内，端口、健康检查与平台表单一致。
- [ ] 健康检查快速返回 200，不调用模型或依赖外部慢服务。
- [ ] SIGTERM、请求取消、上游超时和流式错误均有明确处理。
- [ ] 镜像或前端 ZIP 不含 `.env`、Key、Registry 凭据、用户数据或固定会话信息。
- [ ] 平台镜像校验与真实节点只读拉取已分别验证，包括所需私有 Registry 或 TCR 副本。
- [ ] 每个镜像的 digest、扫描结果和所需 TCR 副本已就绪；复制失败已解决并重试。
- [ ] 平台 TCR Push 在具备按 Agent 限定权限的写凭据前仅用于受信任测试，没有把浏览器镜像 TAR 上传描述成已可用。
- [ ] 重开 `split` 表单后已核对两个镜像和 digest，需要时已确认独立私有仓库访问方案。

### 凭据与入口

- [ ] `UNEX_API_KEY` 与 `UNEX_API_BASE_URL` 只在后端读取并成对使用。
- [ ] `UNEX_AGENT_ID` 与 `UNEX_USER_ID` 由后端运行环境读取，不由浏览器声明授权。
- [ ] 日志、错误、前端响应、浏览器存储和分析工具均不会出现运行时凭据。
- [ ] `single` / `split` 只在受信任隔离环境测试，没有作为已鉴权 HTTPS 生产入口发布。
- [ ] `split` 使用平台明确提供并验证的后端路由，没有硬编码节点地址或未验证的服务发现约定。
- [ ] 测试 `frontend-package` 完整流程前，模式 A ZIP 授权阻止已解除；随后已针对目标场景验证完整客户端鉴权、查询转发和刷新行为。
- [ ] 没有把启动令牌、会话参数或其他秘密保存到浏览器来规避预览限制。

### 数据与节点规格

- [ ] 容器和节点文件系统只存放可丢失、可重建的临时数据。
- [ ] 没有把 `storage_gb` 描述成持久卷、备份或数据保留承诺。
- [ ] 未配置经批准的外部存储时，普通用户上传文件已说明为会话临时数据；发布制品暂存没有描述成用户工作区。
- [ ] `localStorage` 只包含非敏感、可丢弃的界面状态；清除后不影响核心功能。
- [ ] 必须长期保存的数据已接入经平台批准的外部服务，并完成用户隔离与删除设计。
- [ ] 已理解 `gpu_count=1` 表示占用一整台节点，不等于一个物理 GPU。

### 测试与发布

- [ ] 已分别验证首页、静态资源、健康检查、API、流式成功、取消、错误和超时。
- [ ] 平台已独立交付并验证所选节点运行时，上述测试已在真实节点完成，没有用平台页面/API 存在替代运行验收。
- [ ] 已停止并重启实例，应用不会依赖上一次容器文件或内存状态。
- [ ] 当前实际运行 digest 等于本次候选 digest。
- [ ] 审核提交 digest 等于完整测试通过的 digest。
- [ ] 已批准/已发布 digest 等于计划交付给用户的 digest。
- [ ] 已保存脱敏测试记录，并确认日志中没有凭据或敏感数据。
- [ ] 已获得平台对所选拓扑、入口安全、Registry 与数据方案的明确发布确认。
- [ ] 已记录一个已知可用的 digest 和明确回滚步骤。
- [ ] 运行配置已保存，测试通过的制品已在用户启动前提交审核；用户在启动时选择整机 SKU 和时长。
- [ ] 面向用户的价格说明区分模型调用与节点运行，并说明运行计费从 `running` 开始，而不是镜像上传时开始。

镜像、命令、端口、健康检查、拓扑、前端包、节点规格或平台运行时发生变化后，应重新执行本检查表。

模式 A 技术预览适合验证制品、调度和运行适配，不应被当作安全边界、持久化能力或生产可用性的默认承诺。若 Cloudflare 容器交付流程更适合项目，请继续阅读[模式 B Agent 开发与上传指南](agent-development-upload.md)，并同时核对其当前凭据安全与发布限制。
